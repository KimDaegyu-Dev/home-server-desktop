# Human Agent Report

에이전트의 실행 로그를 사람이 판단할 수 있는 한국어 보고서로 바꾸고, 중요한 사실의 누락과 표현상의 문제를 검사한다. 단순한 문체 지침이 아니라 `compose`, `audit`, `revise`, `compare` 절차를 제공한다.

## When to use

- 사용자가 Hermes/Kanban/다중 에이전트의 진행·완료·실패 상태를 보고해 달라고 요청했을 때.
- 장문의 tool result, DAG 실행 기록, 조사/구현/검증 기록을 사람에게 전달해야 할 때.
- 기존 보고서의 이해 난이도, 참조 관계, 검증 주장을 점검할 때.
- 사용자가 `/human-agent-report compose ...`, `/human-agent-report audit ...`, `/human-agent-report revise ...`를 호출했을 때.

간단한 대답, 순수 코드 생성, 기계 간 원시 JSON 전송에는 사용하지 않는다. 근거 없는 사실 채우기나 원본 로그의 조작에는 사용하지 않는다.

## Core principles

1. **결과 우선**: 처음 2~4문장에 현재 상태, 이번에 달라진 점, 검증 여부, 필요한 조치를 전달한다.
2. **Fact ≠ plan ≠ claim**: 설계 확정, 카드 생성, 작업 시작, 작업 종료, 독립 검증 통과를 같은 의미로 쓰지 않는다. 다른 에이전트의 자기보고와 직접 검증 결과를 구분한다.
3. **정보의 지역성**: 먼 문단의 `it`, `those`, `위`, `앞서`, `#18`, `N2`를 독자가 기억하게 만들지 않는다. 시간이 지난 뒤 재언급할 때는 짧은 자연어 이름을 다시 붙인다.
4. **ID 분리**: `t_abcd...`, UUID, 세션 해시는 본문에서 설명보다 먼저 등장하지 않게 한다. 의사결정에 필요 없는 ID는 증거/추적 영역으로 이동한다. 삭제하지 않는다.
5. **논리적 연결**: 조건 → 동작 → 관측 → 결과 → 의미의 연결을 필요할 만큼 쓴다. 메모용 기호, 명사 덩어리, 로그 덤프를 문장으로 착각하지 않는다.
6. **비례적 상세도**: 단순 성공은 짧게, 위험·실패·미검증·DAG 의존성은 충분히 설명한다. 모든 보고서에 고정 템플릿을 강제하지 않는다.
7. **원본 보호**: 원본 증거는 읽기 전용으로 취급한다. 생성된 문서와 검사 파일은 별도의 경로에 저장한다. 확인할 수 없는 수치와 이유는 '미확인'으로 남긴다.

## Procedures

### Compose: 실행 기록 → 보고서

1. 원본 기록, 최신 상태 및 이전 보고서(있을 때)를 읽는다. 누락된 정보는 추정하지 않는다.
2. `references/fact-contract.md`에 따라 중요한 사실을 추출한다. 실행/관측/추정/출처/시점/검증 상태를 구분한다. 가능하면 `facts.json`으로 저장한다.
3. 보고서의 독자가 알고 싶어 하는 것에 따라 핵심 상태, 이번 변화, 증거, 위험, 다음 단계 순으로 재배치한다. DAG의 노드 번호는 유지하되 각 노드의 목적·상태·의존관계를 자연어로 쓴다.
4. 문단에서 참조 거리가 긴 지시어를 풀고, 내부 ID를 추적 영역으로 분리한다. 정확한 명령어·경로·수치는 손상시키지 않는다.
5. 파일을 만든 경우 다음 명령으로 검사한다. **검사 결과가 곧 사실 검증을 뜻하지는 않는다.**

```bash
python3 "${HERMES_SKILL_DIR}/scripts/report_lint.py" --report report.md --facts facts.json
```

`facts.json`이 없으면 `--facts` 옵션을 생략한다. 중대한 오류가 확인되면 수정하고 재검사한다.

### Audit: 기존 보고서 검토

1. 보고서와 가능하다면 근거 문서/원본 로그를 함께 읽는다.
2. 다음 명령으로 정적 검사를 수행한다.

```bash
python3 "${HERMES_SKILL_DIR}/scripts/report_lint.py" --report report.md --format json
```

3. 진단은 **확정 오류 / 점검 필요 / 도구의 한계**로 분류한다. 휴리스틱 경고를 무조건적인 오류로 단정하지 않는다.
4. '무엇이 문제인지 → 왜 이해/판단을 방해하는지 → 어떻게 고칠지'의 형태로 대표 사례를 1~3개 제시한다.

### Revise: 감사 후 재작성

1. 원본 의미와 근거를 유지하고 표현만 수정한다. 상태의 강도를 높이거나 실행하지 않은 작업을 완료로 변경하지 않는다.
2. 원본과 수정본을 비교하여 숫자, ID, 주체, 상태, 조건, 실패 이유의 의미가 보존되었는지 **별도로 의미 검토**한다.
3. 필요하면 `report_lint.py`를 다시 실행한다. 사람이 검토해야 하는 경고가 남을 수 있다.

### Compare: 두 표현의 품질 비교

동일한 사실과 독자, 사용 목적에 대해 결론 파악의 용이성, 참조 해소 부담, 핵심 사실 보존, 검증 상태 표현을 비교한다. 속도 향상·이해도 향상 수치를 실제 사용자 실험 없이 만들어 내지 않는다.

## Evidence contract

`references/fact-contract.md`를 필요할 때 읽는다. 구조화된 facts가 있다면 **중요 사실을 정확히 반영**해야 한다. 스크립트는 명시적 키워드·증거 필드의 존재를 확인할 뿐, LLM의 의미론적 충실도를 증명하지 못한다.

## Output guide

- 간단한 완료: 상태 + 변경 사항 + 검증 결과 (+ 필요한 후속 조치).
- 진행 중/DAG: 현재 요약 → 이번 변화 → 주요 노드 상태 및 의존관계 → 미검증/차단/승인 필요 → 추적 ID.
- 장애: 영향 → 재현/관측 → 확인된 원인과 가설 구분 → 현재 완화 상태 → 다음 검증.
- 일반 보고서 본문에는 작업을 찾을 수 있는 자연어 이름을 쓰고, 정확한 내부 식별자는 '추적 정보' 또는 증거 첨부에 둔다.
- 실제 로그에 없는 성공·수치·시간·단계를 만들어 넣지 않는다. 사용자가 요구하지 않는 장식용 도표나 점수는 추가하지 않는다.

## Verify

- 첫 부분만 읽어도 현재 상태와 검증 범위를 알 수 있는가?
- 문서 중간을 따로 읽어도 지시 대상이 지나치게 멀지 않은가?
- 정확한 ID/명령/수치가 보존되었는가?
- 모든 중요한 주장에 실제 출처가 있는가? 없는 경우 그 사실을 표시했는가?
- `report_lint.py` 결과를 읽고, 휴리스틱 오탐과 실제 문제를 구분했는가?
- 중요한 원본 사실의 의미 보존은 스크립트뿐 아니라 원본과 대조했는가?

## Limits and integration

Skill은 요청 시에 로드되는 절차이며, 설치만으로 모든 에이전트의 최종 응답에 자동 적용되지 않는다. 모든 작업 종료 보고에 강제하려면 Hermes의 실행 종료/디스패처 경로에서 이 Skill을 호출하는 별도 통합이 필요하다. 해당 연동은 실제 런타임에서 테스트하기 전까지 작동을 보장하지 않는다. 스크립트는 표준 Python 3만 사용하며 네트워크/외부 API 호출, 파일 쓰기, 설정 변경을 하지 않는다.
